Panasaurus Wings Rust is an experimental node daemon implementing part of the [Wings HTTP and WebSocket protocol](https://github.com/pterodactyl/wings/tree/develop/router). It is intended for local development and compatibility testing. It is not a complete replacement for upstream Wings.

It authenticates to the panel, loads the servers assigned to its node, reports Docker system information and live container usage, creates and installs servers, starts/stops/restarts/kills containers, delivers console logs over authenticated WebSockets, and sends console commands to container stdin. It validates panel JWT signatures, issuer, audience, server, scope, expiry, permissions and revocations. Existing server data is retained when a container is deleted or rebuilt.

Directory listings, file and folder deletion, and file reads and writes up to 1 MiB are supported with capability-based paths confined to the server directory, including the panel’s EULA acceptance flow. Other file operations, SFTP, uploads, downloads, backups, transfers, egg configuration-file rewriting, automatic crash recovery, graceful egg-specific stop commands, direct TLS, and live node configuration updates are not implemented. Unsupported HTTP operations return `501`; these features must not be enabled for real hosting yet. Stop uses Docker's termination signal and a 15-second grace period. Runtime image entrypoints must launch `STARTUP`, as Pterodactyl yolk images do. Installer containers have a five-minute timeout. This implementation calls the Docker CLI, so Docker and its CLI must be installed.

Build and test with Rust:

```sh
cargo test --locked
cargo build --locked --release
```

Create a node in the panel using the Wings daemon type. Save its generated configuration as `config.yml`, and add the `docker` settings from [config.example.yml](config.example.yml). Set `jwt_audience` to the node's internal connection address, including scheme and port. This must match the JWT audience generated by the panel. `remote` must match the panel URL used as its JWT issuer.

Keep the configuration private:

```sh
chmod 600 config.yml
target/release/panasaurus-wings --config config.yml
```

The volume directory must be an absolute path visible at the same location to the daemon and Docker engine. Give the configured container user permission to write there. Keep the API on a local listener during development. A remote VPS deployment needs a TLS reverse proxy, network restrictions and the missing hosting features above before serving customers.

For the Panasaurus panel's local Colima setup, the private configuration is `.local/wings/config.yml` in the panel checkout. The node's browser address is `http://localhost:8081`, its internal panel address is `http://host.lima.internal:8081`, and the panel is `http://localhost:8080`. The development daemon uses the `colima-panasaurus` Docker context. Credentials and runtime data are ignored by Git.

File writes enforce egg denylist patterns, reject symlink and hardlink aliases, and check aggregate disk usage while holding the server operation lock. The panel selects `/files/create` or `/files/update` for users with only one file permission; these endpoints exclusively create or open an existing file. Daemons without those endpoints reject scoped requests instead of granting extra privileges. Owners and users with both permissions keep the usual `/files/write` endpoint.

Server storage uses fixed-capacity disk images: HFS+ sparse images on macOS, and ext4 loop images on Linux. Linux requires root, `mkfs.ext4`, `mount`, `findmnt`, and `losetup`; its minimum supported quota is 16 MiB. Image metadata consumes part of the allocated space. `build.disk_space` is honored in MiB; a zero allocation uses `system.default_disk_limit_mb` (20480 by default). Images live in `.quota-images` outside container mounts. Game files are stored in the image’s `.server-data` directory, separating filesystem metadata from files exposed to the panel and container. Existing files migrate only while creating an offline container; original files remain in `<uuid>.backup`. A failed migration blocks startup. Back up the image and resize it offline before changing disk allocations.

Runtime containers have read-only root filesystems, a bounded 64 MiB `/tmp`, and rotated logs capped at three 10 MiB files. Docker's private data directory must have capacity for container images and installer layers. Installation scripts are trusted administrator code. API listeners must bind a loopback IP; public access requires a TLS reverse proxy. Plaintext wildcard listeners are refused at startup. Stop and recreate existing containers to apply filesystem protection.

Deletion accepts the panel’s `root` and `files` request, supports recursive folders and bulk selection, and unlinks symlinks without following their targets. Root deletion and parent traversal are rejected. All selected trees are checked for egg denylist protection before deletion starts, and paths are checked again while removing entries. Deletion shares the server operation lock with writes and installation; write and delete tasks retain their lock if an HTTP request disconnects. A request supports up to 10000 selected paths, 100000 entries, and 128 nested directory levels. Missing paths are treated as already removed.

Resource synchronization applies memory, swap, CPU and CPU affinity changes through Docker update. Removing an existing limit and configuration changes that need a new container return an actionable conflict while the server is running; start and restart always fetch the current panel configuration and recreate the container if needed. A failed daemon sync is reported by the panel. Disk allocations still require offline image resizing.

Console access is capped at 128 connections per node, 16 per server, and 2 per account on each server. Authentication permits one attempt per second and console messages permit 20 per second. Connections share resource and log polling for each server. File usage scans use confined directory handles and stop at 128 levels or 100,000 entries.

Minecraft Java hibernation is opt-in. Add the `hibernation` section from [hibernation.example.yml](hibernation.example.yml) to the private node configuration, using the server UUID, its Minecraft Java egg UUID, and its exact primary IPv4 allocation. Keep `enable-status=true` in `server.properties`. Each configured server needs an available listener port; stop its old container before restarting the daemon, then start it from the panel to recreate its TCP mapping. Its world and files are retained. Configuration changes require a daemon restart.

The daemon owns the public Minecraft TCP port and publishes the container's primary TCP port on an automatically assigned loopback port. The daemon and Docker must run on the same host, or use a development Docker context that forwards loopback ports to that host. Secondary TCP allocations and UDP mappings retain their existing mappings. UDP traffic cannot wake a sleeping server. Hytale, Bedrock, legacy Java pings, transfer handshakes, and proxy forwarding authentication are not implemented by this adapter. Ordinary Minecraft Java status and login handshakes are supported; the login and subsequent byte stream are forwarded without changing online-mode authentication. Backends see the proxy address, so IP bans and IP-based plugins need a separate, trusted forwarding integration before public hosting.

The default idle timeout is 10 minutes, with a 2-minute startup grace. A verified zero player count starts the idle timer; players, connected or pending login streams, and missing/invalid status responses reset it. At expiry, a fresh status check and the server operation lock protect the save/stop transition. The daemon sends Minecraft's `stop` console command and waits for the container to exit. It never force kills a server that exceeds the save timeout. Sleeping releases the container's resident CPU/RAM; running servers retain their configured limits and share the freed node capacity.

Server-list pings use cached status and never wake a container. A valid Login Start wakes an automatically sleeping server once, with fresh panel assignment, egg, allocation, and suspension checks. Manually stopped servers stay off. Sleep state is written atomically under the private `.hibernation` directory outside game mounts and survives daemon restarts. Failed wakes have a 60-second retry cooldown; startup concurrency is capped at 4, and TCP connections at 1024 per node plus the configured per-server limit. Cold boots can exceed a Minecraft client's login timeout; reconnect after the server finishes starting. After changing allocation addresses or enabling hibernation on an existing server, start it manually once.

Authenticated server details and console statistics include `hibernation` metadata with enablement, sleep state, player count, idle timeout, and observation errors. The existing running/offline state values remain compatible with the panel. The panel does not yet expose a hibernation configuration form or a dedicated sleeping badge.

The lifecycle integration fixture uses a temporary quota image, a simulated Minecraft endpoint, and a recording Docker executable. On the macOS development host, run it after building:

```sh
cargo build --locked
python3 tests/hibernation.py
```

It checks idle saving, unknown and active player counts, persistent sleep state, status pings, malformed logins, simultaneous joins, opaque stream forwarding, suspension, manual stop, failed-wake cooldown, save timeout, and deletion cleanup. It does not modify existing panel servers.
